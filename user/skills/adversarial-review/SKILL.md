# adversarial-review: 観点を育てる敵対的レビュー

変更を壊す入力・状態・順序を探す立場で差分を読む。読み方の土台は、過去の指摘から作った観点のリスト。リストは 3 階層に分け、レビューのたびに育てる。

| 階層 | 置き場所 | 入れるもの |
|---|---|---|
| 共通 | `~/.claude/skills/adversarial-review/checklists/common.md` | 言語にもプロジェクトにも依存しない観点 |
| 言語 | `~/.claude/skills/adversarial-review/checklists/languages/<言語>.md` | その言語・実行環境・標準的なツールに固有の観点 |
| プロジェクト | `<リポジトリ>/.claude/review/checklist.md` | そのプロジェクトの仕様・構成・約束事に依存する観点 |

## 誰が、いつ使うか

レビューは 2 段にする。利用枠を節約するため、どちらも明示的に指示されない限り差分だけを見る (コードベース全体は見ない)。

| | 普段のレビュー | 敵対的レビュー (このスキル) |
|---|---|---|
| 誰が | 実装したセッション | サブエージェント (会話の前提を持たない) |
| 何で | code-review スキル (effort は medium) | このスキル |
| いつ | 指摘を直すたび | push / PR 作成の前に 1 回。直した量が大きいとき、またはユーザーが指示したときだけ回し直す |
| 範囲 | 前回レビューしたコミットからの差分 | ブランチの差分 (`origin/main...HEAD`) |

実装したセッションは、Agent ツールでサブエージェント (general-purpose) を起動し、次だけを渡す。実装の経緯や、どこが怪しいかの見立ては渡さない (前提を持ち込まないため)。

```
adversarial-review スキル (~/.claude/skills/adversarial-review/SKILL.md) を読み、その手順で <リポジトリのパス> の
<範囲 (例: origin/main...HEAD)> をレビューしてください。読み取り専用です。ファイルを変更しないでください。
観点のリストに無い指摘は「新規」として報告だけしてください。
```

サブエージェントの報告を受けたら、実装したセッションが指摘を直し、直した差分を code-review で確かめる。「新規」の指摘は、実装したセッションが手順 6 で観点のリストに足す。ファイルを書き換える役を 1 か所にまとめるため。

## 手順

### 1. 対象を決める

- 指定が無ければ `git diff origin/main...HEAD`。コミットしていない変更があれば `git diff HEAD` も含める
- PR 番号・ブランチ・パスが指定されたら、それを対象にする
- 範囲は差分に限る。差分の外は、差分の変更が影響する呼び出し元・呼び出し先を確かめるときだけ読む。コードベース全体のレビューは、明示的に指示されたときだけ行う
- 差分が `.md` だけなら、このスキルではなく doc-code-consistency で「書いた内容が実装と合っているか」を確かめる

### 2. 観点を読む

- 共通の `checklists/common.md` は必ず読む
- 差分に含まれる言語の `checklists/languages/<言語>.md` を読む。拡張子が無いファイルは shebang で決める (`#!/bin/bash` なら shell)。今ある言語は `ls ~/.claude/skills/adversarial-review/checklists/languages/` で確かめる
- リポジトリに `.claude/review/checklist.md` があれば、冒頭に領域の索引があるときは、索引と、差分が触れる領域の項目だけを読む (利用枠の節約。迷うときは該当しそうな領域をすべて読む)。索引が無ければ全体を読む。ファイルが無ければ、プロジェクトの CLAUDE.md の約束事を観点の代わりにする

### 3. 読む

- 差分の各 hunk を 1 行ずつ読み、囲んでいる関数全体も読む。変えた関数の呼び出し元を探し、前提が変わって壊れる箇所が無いか見る
- 消した行が守っていたこと (検査、エラー処理、テスト) を挙げ、新しいコードのどこで守られているかを探す
- 観点のリストを 1 項目ずつ当てる。当てはまらない項目は飛ばしてよいが、当てはまるものは実際に確かめる
- リストに無い壊れ方も探す。リストは下限であって上限ではない
- PR 本文やコミットメッセージの説明、テストが通っていることを根拠にしない。コードとテストの中身で確かめる

### 4. 確かめる

- 安く再現できるものは再現する (ガードのスクリプトに入力を流す、テストを 1 件書いて走らせる、境界の値で関数を呼ぶ)
- 再現できず、コードを読んだだけの疑いは「推測」と書いて分ける

### 5. 報告する

指摘ごとに次を書く。重いものから並べる。

- 場所 (`file:line`)
- 何が起きるか (壊れる入力・状態・順序と、その結果)
- 根拠 (再現した結果か、読んだコード)。推測ならそう書く
- 対応する観点の ID (リストに無ければ「新規」)

指摘の後に、当てた観点の ID を並べる (例: `C-01 C-04 SH-02 P-03`)。問題が見つからなければ、確かめた観点を挙げてそう書く。指摘の数を埋めるための弱い指摘は足さない。

プロジェクトのレビューのループ (CLAUDE.md で記録を求めるもの) から呼ばれたときは、最後に「結果: 指摘なし」か「結果: 残す指摘あり」の行を書く。残す指摘には、直さない理由を添える。

### 6. 観点を育てる

読み取り専用で呼ばれたとき (サブエージェントとして呼ばれたときなど) は、この手順を行わない。足す候補を「新規」として報告に書くだけにする。

次の 2 つは、リストに足す候補になる。

- このレビューで出た指摘のうち、どの観点にも当たらなかったもの (「新規」)
- レビューを通った後で見つかったバグ (push のとき、実機、ユーザーの指摘など)。レビューが見逃した理由も考える

足し方:

1. 一般化する。個別の症状ではなく「何を確かめれば見つかったか」を書く
2. 階層を決める。言語にもプロジェクトにも依存しないなら共通、言語や実行環境に固有なら言語、そのプロジェクトの仕様に依存するならプロジェクト。迷ったら狭い方 (プロジェクト寄り) に置き、別のプロジェクトでも出たら広い方へ移す
3. 近い項目があれば、新しく足さずにその項目を直す (確かめ方や例を足す)
4. 形式は各ファイルの既存の項目に合わせる (ID、観点、確かめ方)。書くのは、確かめる観点と確かめ方だけ。経緯 (どこで見つかったか、何が起きたか、いつ統合したか) と、個別のプロジェクトの事情や例は書かない。経緯は git の履歴とレビューの記録に残る
5. 足した項目と置いた階層を、報告の最後に書く
6. 1 ファイルが約 14KB (プロジェクトに `scripts/check-doc-size.sh` があればその上限) を超えたら、足す前に整理する。近い項目を統合し、他の項目に包含される項目と、前提のコードが無くなった項目を落とす。毎回読むので、リストが大きいほどレビューの利用枠を食う

プロジェクトのリストはリポジトリのファイルなので、足したらそのブランチでコミットする。個人スキルのリストは `~/.claude` にあり、コミットは要らない。

## 書き方

- 報告は日本語。前置きと締めの決まり文句を書かない
- 指摘は、何がどう壊れるかを具体的に書く。「堅牢性に欠ける」のような言い方をしない
