# シェル (bash / sh、git フック) の観点

拡張子 `.sh`、shebang が `#!/bin/bash` や `#!/bin/sh` のファイル、`.githooks/` や `.git/hooks/` のフック、Claude Code のフックのスクリプトに当てる。

### SH-01 macOS の /bin/bash は 3.2
- 観点: bash 4 以降の機能 (連想配列、`mapfile`、`${var,,}`) を使っていないか。`set -u` の下で空の配列を展開すると、3.2 はエラーになる
- 確かめ方: `/bin/bash` で実行する。空配列は `${a[@]+"${a[@]}"}` で展開する

### SH-02 コマンド文字列を正規表現で判定するとき
- 観点: ヒアドキュメント (`<<EOF`、`<<'EOF'`、`<<-EOF`)、ヒアストリング (`<<<`)、リダイレクト (`2>&1`、`&>`、`> file`)、引用符の中、`;` `&&` `|` での連結、`bash -c "..."`、`eval`、`$(...)` を含む入力で、判定がずれないか
- 観点 (続き): 同じ意味の別の書き方で判定を抜けないか。長いオプションの略記 (`--no-veri` は git には `--no-verify`)、引用符で囲んだオプション (`"--no-verify"`)、途中の空の引用符やバックスラッシュ (`--no-verif""y`、`--no-ver\ify`)、`$'...'`、同じコマンドにある 2 つ目以降のサブコマンド、ヒアドキュメントの終わりの語に数字や `-` を含むもの (`MSG2`、`END-1`)、`.` (source の別名)
- 観点 (続き): コマンド行に出ない経路で引数や設定を足されないか。環境変数での注入 (`TF_CLI_ARGS` / `TF_CLI_ARGS_<サブコマンド>`、`GIT_CONFIG_*`、`GIT_CONFIG_GLOBAL`)。単ダッシュのオプションの二重ダッシュ形 (Go の flag は `-json` と `--json` を同じに扱う)。オプションと値の連結 (`-d@file`、`-XPOST`、`-sd`)
- 観点 (続き): 「この経路だけ許す」例外を作るとき、(パス) × (HTTP メソッド) × (送るフィールド) で言い切れているか。メソッドを絞らないと、同じパスの別メソッド (リポジトリ本体の DELETE) が通る。パスは正規表現でコマンド全体から探さず、フラグとその値を除いた位置引数をトークンに分けて照合する (パスに見える語を `--jq` の値や引用符の中に置いても判定が変わらないこと)。キー名の除外は引用符を外した文字列で当てる。例外にするのは、引用符・パイプ・展開を含まない安全な文字だけの単独コマンドにする
- 確かめ方: 同じ意味のコマンドを上の書き方で数通りに書き、判定が変わらないかをテストケースにする。例外の経路は、許す経路ごとに GET / POST / PUT / PATCH / DELETE の全部を流し、経路に見える語をフラグの値だけに置いた入力も流す。`&` や `;` で区切る処理は、リダイレクトの `&` を先に取り除く。引用符は中身ごと消さず、外して中身を残す (消してよいのはメッセージなど値だけ)。`sed 's/.*word//'` は貪欲で最後の出現まで消すので、最初の出現までにする

### SH-11 データとして外す部分の決め方 (共通 C-03 の、シェルでの例)
- 観点: コマンド文字列から「データ」(コミットメッセージ、ヒアドキュメントの本文) を外して判定するとき、データとして外すのは許可リスト (文書を書く決まった形) で決める。実行相手を列挙して例外にする方式は、列挙漏れ (`sqlite3`、`ssh`、`awk -f`) と、構文の誤検出 (`$((1<<2))` や引用符内の `<<` をヒアドキュメントとみなし、後ろの実コマンドを外す) で抜ける
- 確かめ方: データの見た目で実際には実行される入力を試す: `cat <<EOF | bash`、`cat > x.sh <<EOF` の次の行で `bash x.sh`

### SH-03 grep は行ごとに判定する
- 観点: 複数行の文字列に `grep` をかけると、判定したい部分と別の行 (ヒアドキュメントの本文など) にも当たる。`grep -o` も行ごとに取り出す
- 確かめ方: 本文の行に判定対象の文字列を書いた複数行の入力を試す

### SH-04 cd の後の相対パス
- 観点: スクリプトの冒頭で `cd` してから引数のパスを使っていないか。呼んだ場所から見た相対パスが別の場所を指す
- 確かめ方: プロジェクト直下以外の場所から、相対パスを渡して実行する

### SH-05 ループの中のコマンドが標準入力を読む
- 観点: `while read` のループの中で呼ぶコマンド (`xcodebuild`、`ssh`、`ffmpeg` など) が標準入力を読み、ループの残りの行を食べていないか
- 確かめ方: 入力を先に変数に読み込むか、中のコマンドに `</dev/null` を付ける

### SH-06 && と || の優先順位
- 観点: `A || B && C` は `(A || B) && C`。`[ ... ] && continue` を `||` とつなぐと意図と違うことがある
- 確かめ方: A、B の真偽の 4 通りで C が動くかを書き出す

### SH-07 set -e / pipefail とパイプ
- 観点: `set -e` が効かない場所 (`if` の条件、`||` の左、コマンド置換の中)、`pipefail` と `head` の組み合わせ (SIGPIPE で失敗扱い) で、失敗を見落としたり、成功を失敗と見なしたりしないか
- 確かめ方: パイプの途中のコマンドを失敗させて、終了コードを見る

### SH-08 git フックの前提
- 観点: `core.hooksPath` が設定されていないとフックは動かない。実行権限が無いと git は hint を出すだけで飛ばす。`--no-verify` で飛ばせる。pre-commit の中では `GIT_INDEX_FILE` がコミットする index を指す (`git commit -a` やパスを指定した commit では一時的な index)。git の設定を上書きする経路は `git config` だけではない: `git -c`、`--config-env`、`GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n`、`-c alias.*` (別名で `--no-verify` を付ける)、`-c include.path`。設定キーは大文字小文字を区別しない (`core.hookspath` も効く)。フックやガードの設定ファイルを Bash で書き換える経路も、`sed -i` とリダイレクトだけではない: `dd of=`、`python -c`、`tee`、`cp` (共通 C-16)
- 確かめ方: フックが「動かない」状態を 1 つずつ作り、検出されるかを見る。index と作業ツリーが違う状態 (一部だけステージ) で commit してみる

### SH-10 git diff --name-only と名前の変更
- 観点: `git diff --name-only` は既定で名前の変更を検出し、変更後のパスしか出さない。パスで「ドキュメントだけか」などを判定すると、`git mv Foo.swift docs/Foo.swift` で変更前のソースが見えなくなる
- 確かめ方: ファイルを動かしただけのコミットで判定を試す。判定に使うなら `--no-renames` を付ける

### SH-09 git の ref と sha
- 観点: push される ref と HEAD は違うことがある。`git push origin other-branch`、`HEAD:branch`、`+branch`、`:branch` (削除)、`--tags`、`--all`。pre-push の標準入力の sha が 0 だけなら削除
- 観点 (続き): ブランチの削除を「取り込み済み」で選ぶとき、`origin/main` と同じコミットを指すブランチは、取り込み直後と切った直後が区別できない。区別できないときは残す側に倒し、残した理由を表示で伝える
- 観点 (続き): `git ls-files` や `git diff --name-only` は、非 ASCII のパス (日本語のファイル名) を、既定で `"\346..."` と引用符つきで出す。末尾 (拡張子) を正規表現で判定すると、日本語名のファイルが通る。`-c core.quotepath=off` か `-z` を使う
- 確かめ方: 上の書き方で push したときに、何を確かめて何を送るかを追う。削除の判定は、切った直後のブランチと、fast-forward で取り込んだブランチの両方で試す。日本語名の `鍵.pem` を追跡して、検査に引っかかるか見る

### SH-12 Claude Code のフックが伝える経路
- 観点: フックの出力が誰に届くかは、終了コードとイベントで決まる。Stop や PostToolUse で exit 0 の stderr は Claude に届かない (Claude に返るのは exit 2 の stderr)。利用者に見せるなら JSON の `systemMessage`。「報告して」「検査を飛ばした」を exit 0 + stderr で出していないか。フックが呼ぶスクリプトの出力を、成功のときに捨てて、中にある警告を消していないか。時間切れ (既定 60 秒、`timeout` で変更) で打ち切られると、止めずに通ることも見る
- 確かめ方: フックの出力ごとに、終了コードと出す先 (stdout / stderr / JSON) を並べ、届く相手 (Claude / 利用者 / どこにも届かない) を書き出す
