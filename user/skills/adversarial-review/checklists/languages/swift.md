# Swift (iOS / watchOS / macOS) の観点

拡張子 `.swift` のファイルと、Xcode のプロジェクト設定 (XcodeGen の `project.yml` を含む) に当てる。Apple のフレームワークの癖もここに入れる。

## 言語とビルド

### SW-01 条件付きコンパイルの両側
- 観点: `#if DEBUG` やカスタムのフラグで分けたコードが、どちらの構成でもコンパイルでき、意図どおり動くか。Release でだけ使う・使わない変数が警告にならないか
- 確かめ方: Debug と Release の両方でビルドする。テストは Debug で動くので、Release 側の分岐はテストで通らないことを前提に読む

### SW-02 ローカライズとテスト
- 観点: `String(localized:)` や `LocalizedStringKey` を通した文字列を、テストで特定の言語の文字 (日本語の読点など) で比べていないか。`String` 変数に入れた文言が訳されない漏れはないか。値だけを入れた `Text("\(a) – \(b)")` は LocalizedStringKey になり、カタログに無いキーができる。訳の対象でなければ `Text(verbatim:)` にする
- 確かめ方: テストを別の言語 (`-testLanguage en`) で走らせる。新しい文言がカタログに入っているかを `xcodebuild -exportLocalizations` で確かめる

### SW-03 Codable と UserDefaults の読み込み
- 観点: 保存したデータのキーが足りない・型が違う・知らない enum の値のとき、デコードが失敗して全体を捨てていないか (`decodeIfPresent`、既定値)。`UserDefaults.bool(forKey:)` は未登録なら `false` を返すので、既定値が `true` の項目は `register(defaults:)` が要る
- 観点 (続き): `UserDefaults` のキーを改名して前の値を移すとき、値とそれに付く最後に変えた時刻を、同じキーから組で取っているか。前の版に戻して使い、上げ直したとき、前の版がまとめて書いた値を、使う人の変更と取り違えないか
- 観点 (続き): 前の版に戻して読む向きで、Optional に変えた項目が nil のときキーを書かない形 (`encodeIfPresent`) を、前の版が必須の項目としてデコードして失敗しないか
- 観点 (続き): 相手の端末や別の版から同期で届く Codable は、デコードできても値の範囲 (有限か、桁、ゼロ割) を検査してから保存と表示に流す。`Int(Double)` は巨大値や NaN で落ちる
- 確かめ方: 古い形式のデータと、知らない値を入れたデータを読ませる。キーを改名したときは、前のキーと今のキーの両方に値がある状態を作り、値と時刻をどちらから取るかを見る。同期で届くものも、前の版の相手が送る形で読ませる

### SW-04 並行性と MainActor
- 観点: `@MainActor` の値を別のスレッドやタスクから触っていないか。`Task {}` の中で self の状態が変わった後の値を前提にしていないか。完了ハンドラが 2 回・0 回呼ばれる場合
- 確かめ方: 非同期の境目 (`await`、コールバック) の前後で、状態の前提が変わりうるかを見る

## Apple のフレームワーク

### SW-05 許可 (HealthKit、位置情報、モーション) の順序と取り消し
- 観点: 許可を求める前に状態を読んでいないか (HealthKit の `authorizationStatus` を `requestAuthorization` の前に呼ぶと、シミュレータで止まることがある)。使っている途中で許可を取り消されたとき、処理が黙って止まらないか。許可のダイアログが、画面を消した後や、別の操作の後に出ないか。許可の回答待ちが `withCheckedContinuation` のとき、回答しないままキャンセルされても、continuation を再開して抜けられるか (共通 C-19)
- 確かめ方: 許可が「未決定」「拒否」「途中で取り消し」の 3 通りで流れを追う

### SW-06 位置情報の精度
- 観点: 「正確な位置情報」がオフ (`accuracyAuthorization == .reducedAccuracy`) のとき、位置から計算する値が 0 になるなど黙っておかしくならないか。位置の飛び・ふらつき・精度の悪い点を除いているか
- 確かめ方: 精度の悪い点、飛んだ点、止まっていてふらつく点の列を入れる

### SW-07 親のデータと付随データの保存 (HealthKit の例)
- 観点: 親のデータ (`HKWorkout` など) と付随するデータ (サンプル、ルート) を別々に保存して、途中で失敗するとやり直せなくならないか。`HKWorkoutBuilder.seriesBuilder(for:)` でルートを作れば、`finishWorkout` で一緒に保存される。失敗したら `discardWorkout` で捨てる
- 確かめ方: 各保存の直後で失敗した場合の、ヘルスケアの中身と、やり直したときの結果を書き出す
- 追加の観点: 保存するデータに重複を防ぐ識別子 (`HKMetadataKeySyncIdentifier` と `HKMetadataKeySyncVersion`) を付けているか。保存後に落ちて再保存したとき、同じデータが 2 件になる

### SW-09 標準のダイアログを自前の覆いに置き換えたとき
- 観点: `confirmationDialog` や `alert` を overlay などの自前の画面に置き換えると、標準のものがしていたことが抜ける。VoiceOver で後ろの要素に届かないこと (`.accessibilityElement(children: .contain)` と `.isModal`)、escape (二本指の Z) で閉じられること、開いたときに読み上げの位置が移ること、ほかの overlay (通知のバナーなど) より手前に出ること
- 観点 (続き): 確認画面の確定のボタン (削除、終了、送信) が、確認を開いたボタンの位置 (二度押しや連打で当たる所) に重なっていないか。開いた直後のタップをそのまま受け付けていないか (共通 C-17)
- 確かめ方: 置き換える前のダイアログの振る舞いを書き出し、新しい画面で 1 つずつ確かめる。VoiceOver は Accessibility Inspector かシミュレータで見る。確かめられなければそう報告する。開く前と後のスクリーンショットを重ね、開いたボタンの範囲が確定のボタンにかかっていないかを見る (いちばん小さい画面でも)。開いた直後の短い間は確定を押せなくするのも手

### SW-08 バックグラウンドと画面を消した後
- 観点: 画面を消した直後の保存やネットワークが、アプリの停止で途中で切れないか (`beginBackgroundTask`)。バックグラウンドで続ける処理に要る `UIBackgroundModes` があるか
- 確かめ方: 「保存の操作の直後に画面を消す」「処理の途中でロックする」の流れを追う。実機でしか確かめられないものは、確かめていないと報告に書く

### SW-10 プライバシーマニフェスト
- 観点: App Store に出すアプリに `PrivacyInfo.xcprivacy` があり、使っている必須理由 API (UserDefaults、ファイルのタイムスタンプ、システム起動時間、ディスク容量) とその理由を宣言しているか。ビルドは通るので、提出するまで気づけない
- 確かめ方: `git ls-files | grep xcprivacy` で有無を見る。`UserDefaults`、`creationDate`、`systemUptime` などを使うコードを grep し、宣言と照らす。ターゲットごとに (iPhone、Watch) 必要になる

### SW-11 `@State` の初期値と副作用
- 観点: `@State private var x = Foo()` の初期値は、親の body が評価されて View が作り直されるたびに評価される (保持されるのは最初の 1 つだけ)。`CLLocationManager` や `HKHealthStore`、タイマー、通知の購読など副作用を持つオブジェクトをここで作っていないか。使わない画面や設定でも作られていないか
- 確かめ方: `@State` の初期値の式にクラスのインスタンス化があれば、生成時の副作用 (delegate の登録、許可の問い合わせ、購読) を読む。必要なときに optional の `@State` へ作る形にできないか考える

### SW-12 ファイルを分けるために外した `private`
- 観点: 拡張を別ファイルに移すため `private` / `private(set)` を外したとき、書き換えられる範囲が広がっていないか (ビューから状態を直接書き換えられる、など)。コメントだけで守っていないか
- 確かめ方: 外した宣言を grep し、型の外から代入している箇所が無いかを見る。遷移用のメソッドを 1 つ用意して書き込みをそこに絞れないか考える

### SW-13 ActivityKit の表示を引き継ぐ・終了するとき
- 観点: `Activity.end()` を `Task` で頼んだ直後に `Activity.activities` を読むと、終了が済むまで終わりかけの表示が残っていて、それを引き継いで更新してしまう。更新は終了の後に実行されるので効かず、新しい表示が出ない。引き継ぐのは `activityState == .active` で、終了を頼んでいない (ID を覚えておく) ものに限る
- 確かめ方: 終了と開始を同じ呼び出しで続けたとき (終了の直後に別の出どころの開始が届く) の、引き継ぐ表示を追う
