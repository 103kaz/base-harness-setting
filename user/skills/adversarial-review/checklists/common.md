# 共通の観点

言語にもプロジェクトにも依存しない観点。項目は ID で指し、消した ID は使い回さない。各項目には、確かめる観点と確かめ方だけを書く。経緯 (どこで見つかったか、何が起きたか、いつ統合したか) と、個別のプロジェクトの事情や例は書かない。言語に固有の観点は `languages/` に、プロジェクトに固有の観点はリポジトリの `.claude/review/checklist.md` に置く。14,500 バイトを超えたら、足す前に統合する (リポジトリの `scripts/check-doc-size.sh` があれば警告が出る)。

## 入力と境界

### C-01 境界値
- 観点: 0、空 (空文字列・空配列・空ファイル)、上限、負数、1 件だけ、とても大きい値で壊れないか
- 確かめ方: 変えた関数の引数と、ループの回数・インデックスの端を 1 つずつ当てる

### C-02 判定の範囲が広すぎる・狭すぎる
- 観点: 文字列やデータ全体への判定が、別の文脈 (後に続く別のコマンドの引数、本文やコメント、別のフィールド) に当たらないか。逆に、区切り方を誤って判定すべき部分が見えなくなっていないか
- 確かめ方: 判定の対象を「どこからどこまで」と言葉にし、その外側に同じ文字列を置いた入力と、区切り文字 (`&`、`;`、改行、引用符) を途中に挟んだ入力を試す。検査から外す条件 (`.*` のような広い除外) は、外したい対象 (`.git/` の中) だけに絞れているか。除外に当たる実在のパスを列挙し、検査してほしいもの (`.claude/`) が混ざっていないかを見る

### C-03 データとして渡るものを、命令として解釈しない (逆も)
- 観点: メッセージや本文などデータの部分を、命令や引数として判定していないか。逆に、実行されるもの (シェルに渡す文字列) をデータとして判定から外していないか。同じ種類の判定を足すときは、既存の判定と同じ前処理 (データを外した文字列) を通す
- 確かめ方: データ側に命令らしい文字列を入れた入力と、データの見た目で実際には実行される入力の両方を試す。データとして外すのは、許可リストで決める (シェルなら SH-11)

### C-04 権限と入力の悪用
- 観点: 外から来る値 (ファイル名、URL、コマンドの引数、他人の PR) で、意図しない操作や情報の漏れが起きないか
- 確かめ方: 攻撃者が選べる値を挙げ、それぞれ最悪の値を入れたときの動きを追う

## 失敗と順序

### C-05 失敗経路とエラー処理
- 観点: 失敗したときに、エラーが握りつぶされていないか、中途半端な状態が残らないか、利用者に何が起きたか伝わるか
- 確かめ方: 各 `try` / 戻り値の検査 / 外部呼び出しで、失敗したら次にどの行が動くかを追う

### C-06 途中で失敗したときの整合性
- 観点: 複数の保存・送信を順に行う処理が途中で失敗したとき、やり直せる状態が残るか。一部だけ成功してやり直すと二重になる、一部を二度とやり直せない、とならないか (「保存の成功」と「保存済みの印を付ける」の間で落ちたときも。逆に、続く処理を始める前に「済んだ」印を立てると、処理が何もせず (空配列、nil、前提の不足) 終わったときも印が立ち、二度と行われない。印は結果を見てから立てる)。「頼む」と「確定する」が別の呼び出しで、頼む側が印を先に立てる遷移 (永続化された印を含む) は、依頼が失敗したり通知が来なかったりしたとき、印だけが残って次の別の通知を誤って解釈しないか。保存先に同じ操作を 2 回しても 1 件になる印 (冪等キー、同期用の識別子) を付けられるなら付ける。付けられないなら、二重になりうることを文書に書く
- 確かめ方: 各ステップの直後 (成功の直後、印を付ける直前を含む) で落ちた場合を 1 つずつ書き出し、再実行 (次の起動) の結果を見る

### C-07 並行実行・再入・二重実行
- 観点: 同じ処理が重ねて走る (連打、前の処理の完了前に次が始まる、コールバックが 2 回来る) と壊れないか
- 確かめ方: 状態を変える入口ごとに「実行中にもう一度呼ばれたら」を考える。フラグは立てる場所と戻す場所の両方を見る

### C-08 確かめた対象と、実際に使われる対象が同じか
- 観点: 検査・ビルド・レビューをした対象と、その後で反映される対象 (commit される index、push される ref、検査の後に書き換わったファイル) がずれていないか。前提の確認は、その前提に頼る検査すべてより前に置く
- 確かめ方: 「何を確かめたか」と「何が使われるか」を同じ言葉で書き、間に書き換えが入る余地 (生成、別ブランチ、未ステージの変更) を探す

### C-09 前提が満たされないとき黙って飛ばされないか
- 観点: 設定・権限・ファイルの有無などの前提が崩れたとき、エラーにならず何もしないまま成功扱いになっていないか。検査を飛ばす条件に入ったとき、飛ばしたことが警告として出るか。「前に送った値を覚えて、同じなら送らない」判定が、プロセスの再起動で覚えた値が初期値に戻っても成り立つか (復帰した直後に、前の値と違う終了を送れるか)
- 観点 (続き): 破壊的な操作 (サイト全体の置き換え、上書きのデプロイ) の条件が、前提の一部だけを見ていないか。前提が欠けたとき、比較や引き継ぎを飛ばして実行に進まないか。「前の状態が取れない (404、空)」を「初回」と同じに扱っていないか。初回は、明示の指定のときだけ通す
- 観点 (続き): 「変更があるときだけ検査する」の判定が、作業ツリーの未コミットの変更だけを見て、同じ回の中でコミットされた変更を取りこぼさないか。外部の検査ツールが「0 件を検査、問題なし」で成功を返したとき、対象を取れなかった (範囲の指定の誤り、git の失敗) のと区別しているか
- 確かめ方: 仕組みが動くための前提 (設定値、実行権限、環境変数、ツールの有無、`origin/main` の有無) を挙げ、1 つずつ外したときの動きと出力を見る。検査ツールには解決できない範囲を渡して、終了コードを見る

## 互換性と環境

### C-10 保存形式の後方互換
- 観点: 保存したデータ (設定、途中の記録、キャッシュ) を、前の版が書いたものでも読めるか。読めないときに黙って消したり、上書きしたりしないか。項目の名前 (キー) を変えて前の値を移すときの、値と時刻の取り違えは SW-03
- 確かめ方: 項目が足りない・余分・型が違う・壊れているデータを読ませる。同期で届くものも、前の版の相手が送る形で読ませる。今の版が書いたデータを前の版で読む向きも見る (Swift は SW-03)

### C-11 テストが環境に依存していないか
- 観点: 言語・地域・タイムゾーン・機種・並列実行など、実行する環境で結果が変わるテストがないか
- 確かめ方: テストが読む環境の値を探し、別の値 (英語、UTC など) で動かす

### C-12 構成ごとの分岐を、すべての構成で確かめているか
- 観点: 条件付きコンパイルや設定による分岐 (Debug / Release、開発版 / 製品版、機能フラグ) の、すべての側がビルド・テストされているか
- 確かめ方: 分岐を列挙し、それぞれの側で動かしたかを確かめる。片方でしか使わない変数や関数が、もう片方で警告やエラーにならないかも見る。`.gitignore` 済みの生成物の存在を検査していないか (生成前の clone で止まらないか)

## テストと検証

### C-13 テストが検証になっているか
- 観点: アサートが足りない、モックしすぎ、失敗しても通る (条件が常に真)、足した処理を通っていないテストがないか
- 確かめ方: 直した箇所を元に戻したらテストが落ちるかを考える (できれば実際に戻して走らせる)
- ガードや検査にケースを足したときは、変更前のコードで流して、結果 (止める / 通す) が変わるケースが 1 つ以上あるかを見る。変更前でも同じ結果のケースは、回帰を検出しない
- 「NG になるはず」の否定テスト (`! cmd`) は、コマンドが無い・構文エラーでも通る。出力の理由まで確かめる。確認用のスクリプトは、通す側のケースも複数入れ、全部止める・全部通すスタブに差し替えて落ちるかを見る。設定の「登録済み」は語の grep でなく構造で読む

### C-14 消した振る舞いが別の場所で守られているか
- 観点: 消した・置き換えた行が守っていた検査やエラー処理が、新しいコードのどこかで守られているか。仕組みを置き換えるときは、古い仕組みがしていたことを全部書き出してから消す
- 確かめ方: 消した行ごとに「これが無いと何が通るか」を書き、新しいコードで止まる箇所を探す

### C-15 誤判定の向き
- 観点: 検査の誤判定が「止めすぎ」か「通しすぎ」か。通しすぎの方が重い。止めすぎも頻繁なら、回避策を探す癖がついて検査が形だけになる。破壊的な操作 (ブランチの削除など) の対象を「取り込み済み」で選ぶとき、空の状態 (新しく切っただけのブランチ) が取り込み済みと同じ判定にならないか。区別できないときは、残す側に倒し、残した理由を表示で伝える (git は SH-09)
- 確かめ方: 検査ごとに、通してはいけないのに通る入力と、止めなくてよいのに止まる入力を 1 つずつ考える。語が「実在するか」を調べる検査では、`*` を含む語、`a/b` の並記、`path:12`、これから作る名前で、毎日同じ誤検出が出ないか

### C-16 「検査を通した」という印を、検査の外から作れないか
- 観点: 検査の結果を記録ファイルやフラグで残し、それを見て後の処理を飛ばす仕組みで、検査を通らずに印だけを書けないか。検査の仕組み自身 (フック、ガード、その設定) を書き換える経路が、印と同じ強さで守られているか (git の設定を上書きする経路は SH-08)
- 確かめ方: 印を書ける経路を、読む側のコードからすべて挙げる。ガードの判定に書き換えの文字列を実際に流して終了コードを見る。Edit で ask になるパスごとに、同じパスへの Bash の書き込みも止まるかを見る。止めきれないなら、印が自己申告であることを書く

### C-17 取り消せない操作の確認で、二度押しが確定に当たらないか
- 観点: 自前の確認画面で、確定のボタン (削除、終了、送信) が、確認を開いたボタンの位置 (二度押しや連打で当たる所) に重なっていないか。開いた直後のタップをそのまま受け付けていないか
- 確かめ方: 開く前と後の画面を重ねて見る。iOS の確かめ方は SW-09

### C-19 待つ処理の出口
- 観点: 「条件が満たされるまで待つ」処理 (センサーの精度待ち、通信の完了待ち、許可の回答待ち) の出口が、利用者の「キャンセル」だけになっていないか。条件が永久に満たされない状態 (許可が無い、精度を落とす設定、エラーが続く) を先に判定して抜けるか、失敗を知らせる経路か時間切れがあるか。キャンセルで待ちを止める仕組みが働くか (Swift の許可待ちは SW-05)。待ちの再開口 (continuation など) を共有の変数で持ち、キャンセルの処理がその変数ごと再開するときは、遅れて届いたキャンセルが、あとから始まった別の待ちを終わらせないか (待ちごとの番号で照合する)
- 確かめ方: 待ちのループや `await` の抜ける条件を全部数え、永久に満たされない状況で画面に何が出続けるかを見る

### C-20 外部の API や CLI で「済んだか」を判定するとき
- 観点: gh などで「マージ済み」「完了」を判定して破壊的な操作をするとき、(1) 絞り込みが足りているか (base、fork 元、同じ名前の再利用)、(2) 呼び出しの失敗 (未ログイン、オフライン、権限) と「該当なし」を区別しているか。`2>/dev/null || echo 0` で握りつぶすと、判定できていないことを利用者が知れない。(3) 一覧取得の件数の上限に届いて古い物が切れていないか (届いたら失敗扱い)。(4) 結果の形 (JSON の配列か) を確かめてから「該当なし」と判定しているか
- 確かめ方: 取得結果が対象だけに絞られているかを、条件を 1 つずつ外して確かめる。外部の呼び出しを失敗させ (無効なトークンなど)、出力に原因が出るかを見る

### C-21 生成したファイルの再実行と上書き
- 観点: 雛形をコピーした後に中身を書き換える (プレースホルダを埋める) とき、2 回目の実行の「同じか違うか」の比較が、書き換え前の元と比べていないか (毎回「違う」になる)。上書きの経路 (`--force`) で、書き換えの手順が飛ばされていないか
- 確かめ方: 初回 → 編集せずに 2 回目 → 上書きの順に実行し、表示と結果のファイルを見る
