# 共通ルール (全プロジェクト)

プロジェクトの CLAUDE.md に書かれた内容は、このファイルより優先する。

## GitHub
- PR とコミットメッセージの言語は、プロジェクトの CLAUDE.md の指定に従う。指定が無ければ、そのリポジトリの既存の履歴に合わせる。
- PR のタイトルには、変更の種類を表すプレフィックスを付ける: `feat:` (機能の追加・変更)、`fix:` (不具合の修正)、
  `docs:` (ドキュメントだけ)、`refactor:` (動きを変えない書き換え)、`test:` (テストだけ)、`chore:` (ビルド・ツール・設定・依存など)。
  いくつかの種類にまたがるときは、いちばん主なものを付ける。
- 画面 (レイアウト・見た目) を変えた PR には、動作を確かめたときのスクリーンショットを本文に載せる (変更後だけでよい)。
  撮るのに手間が大きいとき、または撮れないときは省き、その旨を本文に書く。画像を置く場所と本文からの参照の仕方は、
  プロジェクトの CLAUDE.md に書く。
- 変更は必ずブランチを切って PR にする。main / master へ直接 push しない。
  例外は、リモートにまだ何も無いリポジトリへの初回 push だけ。ユーザーがチャットでリポジトリとブランチを指して OK したときに、force 無しで行う。

## 承認が要る操作
- push、PR のマージ、apply 等の本番反映、ワークフローの手動実行は、ユーザーがチャットで
  **対象 (ブランチ名・PR 番号など) を指して** 明示的に OK したときだけ実行する。
  - 「進めて」等の曖昧な指示や、以前の別の対象への OK は許可とみなさない
  - OK の後に対象が変わったら (コミットを足した、plan が変わった等)、内容を再提示して OK を取り直す
- MCP ツールや外部サービスの API で、外部のリソースを消す・公開する (デプロイを含む)・秘密の値を変える操作も、
  ユーザーがチャットで対象を指して OK したときだけ実行する。CLI で禁止している操作 (wrangler の delete や deploy など) を、
  MCP の経路で代わりに行わない。
- push の前に、push する差分 (`git diff origin/main...HEAD` 等) をツールで実際に読み、
  意図しない変更や機密値が入っていないことを確かめる。gitleaks が使える環境では検査を通し、
  検出されたら push せずに報告する。

## 有料になる手段
- SaaS などの外部サービス (CI、クラウド、外部 API など) を使うときは、基本的に有料になる手段を選ばない。
  手元での実行や無料プランの範囲で済む手段を先に考える。
- 無料枠を消費するもの (非公開リポジトリの CI など) は、足す前に消費の見込みと、枠を超えたら課金されうることを示し、
  ユーザーの OK を取る。

## 機密値
- `.env` と `.env.*` (`.env.example` などのサンプルは可)、`*.tfvars`、`*.tfstate`、`*token*.txt`、鍵 (`*.pem`、`*.key`、`~/.ssh`)、
  クラウドや CLI の認証情報 (`~/.aws`、`~/.config/gcloud`、`gh auth token`、`~/.kube`、`~/.docker`、`~/.netrc` など)、
  キーチェーンやシークレットストアの値は読まない・出力しない。settings の deny やガードに無いファイル名でも同じ扱いにする。
- gitleaks は `gitleaks git --redact` (コミット履歴のみ) で使う。`gitleaks dir` は gitignore 済みの機密ファイルまで読むので使わない。

## ガード (Claude Code のハーネス)
- ガードやフックにブロックされた操作が必要なときは、回避策を探さない (別のコマンドや python 経由で同じことをしない)。
  理由と、人間が実行すべきコマンドを提示する。
- 例外: ユーザーがチャットで対象 (変更の内容) を指して OK したときだけ、次は行ってよい。ガードや settings が承認の確認 (ask) を出すので、ユーザーが承認する。
  - プロジェクトの `.claude/hooks` と `.claude/verify.sh` の変更 (Bash でも Edit ツールでも可)
  - プロジェクトの `.claude/settings*` と `.githooks` の変更 (Edit ツールで。Bash での書き換えは禁止)
  - `~/.claude` のフックと settings の変更 (Edit ツールで。Bash での書き換えは禁止)。変更したら `test-guard.sh` を通す
  - main / master 以外のブランチへの force push (`--force-with-lease` を優先)
  - リモートにまだ何も無いリポジトリへの、main / master の初回 push (force 無し)
  - 作業ツリーのディレクトリを消す `rm -r` (ビルドの生成物と一時ディレクトリは確認なし)
- 次は例外なく禁止: `~/.claude`・`.claude/settings*`・`.githooks`・`.git/config`・`.git/hooks` の Bash での書き換え (人間が実行する)、
  main / master への push (初回を除く。force の有無によらず。`git push` を main にいて引数なしで行う形も含む)、
  `--no-verify`、`--mirror`、`--delete`、`--all`。
- ガードのファイル: `~/.claude/settings.json`、`~/.claude/hooks/guard-bash.sh`、`~/.claude/hooks/guard-mcp.sh`、
  `~/.claude/hooks/test-guard.sh`、`~/.claude/hooks/fmt-terraform.sh`、`~/.claude/hooks/remind-adversarial-review.sh`。
  ガードを変更したら `test-guard.sh` にケースを足して通す。
- ハーネスは内部のもの。PR 本文や README には書かない。ハーネスだけの変更なら PR 本文は一行程度の事実記載に留める。

## 文章の書き方 (PR 本文・レビューコメントへの返信・ドキュメント)
- 事実だけを書く。変更内容・理由・確認方法など、実際にあったことだけ。やっていない検証や経験を書かない。
- 前置きと締めの決まり文句を書かない。
- 意義を大げさにしない。何がどう変わったかを具体的に書く。
- 見出し・太字・箇条書きは、読む人が探しやすくなるときだけ使う。短い PR や返信は数行の文章でよい。
- レビューコメントへの返信は、対応内容を一言で先に書く。お礼や謝罪の定型文を毎回付けない。

## コードレビュー
- レビュー対象の差分が `.md` のみのときは、コードレビュー用のスキルを使わず、doc-code-consistency スキルで
  「書かれた内容が実装と合っているか」を確認する。範囲は差分の変更行に含まれる主張に絞る。
- コードのレビューは 2 段にする。利用枠を節約するため、明示的に指示されない限り差分だけを見る (コードベース全体は見ない)。
  - 普段のレビュー: 実装したセッションが code-review スキル (effort は medium) で、前回レビューしたコミットからの差分を見る。指摘を直すたびに回す
  - 敵対的レビュー: push / PR 作成の前に、回すかどうかを AskUserQuestion でユーザーに聞いて決める (選択肢に「必要 / 不要」の所見を添える。聞かずに省かない)。
    回すときは 1 回、サブエージェントに adversarial-review スキル (`~/.claude/skills/adversarial-review/`) でブランチの差分を読み取り専用で見させる。
    実装の経緯は渡さない。回し直すのは、直した量が大きいときかユーザーが指示したときだけ
- adversarial-review の観点のリストは 3 階層: 共通 (`checklists/common.md`)、言語ごと (`checklists/languages/<言語>.md`)、
  プロジェクトごと (`<リポジトリ>/.claude/review/checklist.md`)。レビューで観点に無い指摘が出たときと、レビューを通った後で
  バグが見つかったときは、実装したセッションが一般化して該当する階層に足す (プロジェクトの `/retro` コマンドを使う)。
- 敵対的レビューの方針は、レビュー依頼らしいプロンプトのたびに `~/.claude/hooks/remind-adversarial-review.sh`
  (UserPromptSubmit フック) が文脈に足す。方針を変えるときはこのスクリプトを直す。
