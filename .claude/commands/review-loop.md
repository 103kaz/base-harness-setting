---
description: 実装→レビュー→修正の開発ループを 1 周回す (push / PR 作成の前に使う)
---

現在のブランチの変更に対して、次の順で開発ループを回す。範囲は差分だけ (コードベース全体は見ない)。

1. `.claude/verify.sh` を実行し、通ることを確かめる。落ちたら先に直す。終了コード 78 は「検証コマンドが未設定」の意味なので、そのことをユーザーに伝えて先へ進む。
2. code-review スキル (effort は medium) で、前回レビューしたコミットからの差分を見る。
3. 指摘を直す。直すたびに 1 に戻る。指摘が出なくなるまで繰り返す。直さない指摘は理由を書き残す。
4. 差分が `.md` のみなら、2 の代わりに doc-code-consistency スキルで「書いた内容が実装と合っているか」を確かめる。
5. CLAUDE.md のコマンドの表にある「PR 前のテスト」を回す。検証ループに入れていない重いテストを、ここで回す。落ちたら直して 1 に戻る。表が `TODO` のままなら、そのことをユーザーに伝えて先へ進む。差分が `.md` のみなら飛ばす。
6. この変更が不具合の修正 (ブランチ名が `fix/` で始まる、またはユーザーが不具合の修正だと言った) なら、直したバグが、以前のレビューを通ったコードにあったかを確かめる。修正前の行を `git blame origin/main -- <ファイル>` で辿る (HEAD で辿ると修正のコミット自身が出る)。行を足しただけの修正なら、足した場所を囲む関数の行を辿る。出てきたコミットが、`.claude/commands/review-loop.md` を足したコミット (`git log --diff-filter=A --format=%H origin/main -- .claude/commands/review-loop.md`) より後に `origin/main` に入ったものなら、レビューを通ったとみなす。そうなら、`/retro` の手順で「何を確かめれば見つかったか」を観点のリストに足す。
7. push / PR 作成の前に、敵対的レビューを回すかどうかを AskUserQuestion でユーザーに聞く (選択肢に「必要 / 不要」の所見を添える。聞かずに省かない)。回すときは、サブエージェントに adversarial-review スキルで `origin/main...HEAD` を読み取り専用で見させる。実装の経緯は渡さない。
8. 敵対的レビューで「新規」とされた指摘は、`/retro` の手順で観点のリストに足す。
9. 最後に「結果: 指摘なし」か「結果: 残す指摘あり (理由つき)」を報告する。

push・PR 作成・マージは、ユーザーがチャットで対象を指して OK したときだけ行う。このコマンドは push までは行わない。
